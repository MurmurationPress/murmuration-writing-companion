# Proposal for derived book local numbering

Status: proposal only. No schema migration, property removal, query edit or compiler change has been applied. This is separate from merged #256 and the subsequent interaction/performance correction. Keep `parent` and `manuscript_order_key` authoritative; derive book-local positions for display/export and retire automatic persistence of **all three** reporting fields after their consumers are migrated.

The dependency audit changes the compatibility assessment: available private Bases definitions really use `manuscript_sequence` for sorting. Turning persistence off silently would leave those reports stale. Codex Press also has generic metadata readers, even though its ordering engine does not name the reporting fields. Absence of literal runtime references is not proof that export consumers are independent.

## Audit scope

MWC main `50e5a400481e59f9b698548cb14f0b2c02445f94` (merged #256); Codex Press public main and the local clean checkout both at `93af44922cdb1b83b6166c4f8429d7d9f5b32c07`, checked against origin on 1 October 2026. Searches include exact property names, their exported constants/camel-case values, scripts, tests, examples, docs, generic metadata access and export call sites.

Available legacy Codex Press, website and animation working trees were searched read-only for the three exact identifiers; no literal references were found. This is a text audit, not a guarantee about dynamically assembled property names. The author vault's `.base` definitions were inspected **read-only**, recording field counts and sort declarations only. No manuscript prose, query content or private paths are reproduced here. Other private Markdown queries, inline metadata expressions, installed third-party plugins, templates, external scripts and other devices remain unverified.

The earlier statement that Codex Press had no references to the numeric names was too broad: its dedicated ordering code does not depend on them, but the integration harness does, and generic export/query readers can. This proposal distinguishes those cases.

## Recommended model

Keep the existing stable sibling order keys. An insertion normally allocates a midpoint key without editing neighbouring notes; reparenting changes the moved node's `parent` and key. Exhausted key space can still require an explicitly reviewed sibling-local rebalance. Derive a continuous **book scene number** and, if useful, an outline label such as `1.2` from the resolved tree at display/export time. Neither label is a stable identifier or an authoritative property.

Do not persist legal-style numbering as hierarchy. Inserting before `1.2` would rename later siblings and descendants; moving a subtree would rewrite every descendant prefix and destabilise number-based references. Retaining both dotted authority and `parent`/key would create competing facts. Use ordinary links for scene identity and allow Obsidian rename handling to maintain them; no new identifier scheme is needed for this change.

The current model permits Parts directly under Books, and Scenes under Books or Parts. Arbitrarily nested Parts are a separate MWC/Codex Press schema change. A label format with arbitrary depth does not make those structures valid. Preserve diagnostics, explicit `scene-draft` exclusion, Trash handling and legacy preparation. Do not invent positions for unresolved parents/keys.

Display and export must declare their scope: manuscript membership and a filtered export selection may have different scene counts. Reuse the compiler's authoritative selected order for export numbering; do not let a display filter silently become compiler authority. Mixed direct Scenes and Parts must retain the same traversal order. Neither excluded scenes nor Parts should inadvertently increment a continuous Scene count.

## Treat manuscript sequence as part of the same retirement

M is not merely another name for the Book scene count: its Book segment depends on library title ordering, its root segment on Book children, and its last segment on Part children. A direct Scene ends with `000`. Local reorder/insert can change many M values even without B/S; renaming a Book can change the Book segment across Books.

Stopping only S removes cross-Book count-offset churn but leaves local M writes. Stopping B and S still leaves the measured local mass writes. The target mode must disable automatic create/update/**cleanup** of B, S and M together. Preserve their last stored values as explicitly legacy snapshots until an author chooses cleanup; do not delete them during startup, reads, prose edits or detachment. Membership/export must remain independent of those stale snapshots.

## Compatibility sequence before enabling the new mode

1. **Provide derived readers first.** MWC display/export should calculate positions from the shared resolved order. Add compiler-side in-memory projections at the export boundary where consumers need them; never write compiler-derived positions back to scene notes. Verify all supported output formats, not just order assembly.
2. **Migrate the two confirmed sorting reports and the Book-number display.** Prefer Book-scoped derived views or explicit generated report snapshots. A native Bases formula that reads parent keys is an option only after verifying actual Obsidian and Codex Press behaviour, including mixed root Scenes, repeated keys under different Parts, missing metadata and exclusions. Sorting solely by scene `manuscript_order_key` is wrong across sibling groups. No verified replacement query syntax is promised here.
3. **Audit indirect uses.** Check private `=this.*` expressions, Dataview/Bases Markdown embeds, templates and external tools for these identifiers. For a required scalar-property consumer, offer the existing explicit “Rebuild manuscript reporting sequence” compatibility action, clearly described as a snapshot that can become stale. Do not silently substitute snapshot semantics for a live report. Series-wide output need not be retained for this author's workflow, but unknown consumers must be explicitly accepted or migrated.
4. **Use one versioned, project-wide reporting policy.** Proposed modes are legacy automatic reporting and derived book-local reporting. Existing vaults remain in legacy mode until their consumer transition is accepted; new projects can default to derived mode. Store the policy once in portable project configuration, not per Scene, and document which MWC versions honour it. The exact configuration location/schema needs implementation design; no new store is introduced by this proposal. Update all devices/plugins that can regenerate reports before switching, because old clients ignore a new policy.
5. **Stop automatic writes without deleting existing data.** Derived mode disables startup/settled reporting reconciliation and any indirect automatic call sites. The explicit compatibility snapshot command remains deliberate, and its series behaviour is clearly specified rather than inferred from the selected Book. Disabling/re-enabling MWC must not silently re-enable automatic reporting.
6. **Make cleanup separate and reversible.** Offer a previewed optional removal of the three obsolete fields only after the consumer audit, with backup/Undo and exact unrelated YAML/prose preservation. No cleanup is required for correct compiler membership/order. Old raw Undo snapshots may legitimately restore old fields; that must not re-enable the automatic writer. A downgrade to an older MWC can regenerate values and needs a documented compatibility warning.

This avoids a new per-scene schema and a new mass-renumbering mechanism. It also respects the existing unnamespaced-field mismatch with Constitution Article I: do not resolve it by continuously writing three renamed `mwc_` properties on every scene. A generated report can use namespaced disposable metadata without rewriting manuscripts.

## Acceptance and rollback requirements

Use disposable fixtures to prove zero automatic B/S/M frontmatter writes on startup, prose edits, metadata changes, insertion, reorder, reparent, detach/restore, Book rename and Book switch in derived mode. Verify fresh display numbers, unchanged authoritative keys and identical compiler order/exclusions. Cover direct Scenes, Parts, duplicate/missing keys, invalid structure, legacy preparation, exact Undo, renamed links, filtered exports and mixed device/version behaviour.

Run MWC tests and the Codex Press membership/integration regressions in both modes; test manuscript/PDF/EPUB inline metadata and native query output with present, absent and stale reporting fields. The confirmed Bases consumers must either show correct live derived order or be explicitly accepted as manual snapshots. Missing generic metadata currently becomes empty in inline export; do not silently ship that output change for a required field.

Rollback restores the project reporting policy and allows an explicit projection rebuild from authority. It does not restore ordering from old counters. Require a separate reviewed implementation PR and acceptance on a disposable copy before any live-project transition. No schema or vault changes are included in the immediate performance PRs.
